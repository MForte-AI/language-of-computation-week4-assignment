# Comparison: my books.db and my partner's books.db

**The two databases do not hold the same data.**

- My books.db: **10,014 books**
- My partner's books.db (Tio, `partner/books.db`): **10,014 books**
- Books only in mine: **0**
- Books only in my partner's: **0**
- Books in both with a different value: **892** (892 values)

## How the comparison was done

- Partner's database downloaded from https://github.com/tioluwanimofe/language-of-computation-week4-assignment/raw/assignment/books.db and saved as `partner/books.db`. My books.db was not changed.
- Both databases have one table, `books`, with the same 24 columns under the same names: the 23 CSV columns plus `changes_repairs`.
- Two rows are the same book when they have the same `book_id` (rules.md, section 8).
- Columns compared: all 24, matched by name. No column was left out: neither database has a column that only records when a row was loaded.

All of these books have an isbn13 in scientific notation with exactly 13 digits and 16 characters, such as `9.7806182603e+12` (The Hobbit).

## Why our data differs

There was no difference in our rules, yet the column with the issues state different things for 892 books. These books are labeled differently because of an interpretation of one of the rules. In the rules.md the answer 8, “Add the digit-count label only when the value also has the wrong number of characters (not 10 or 13)” can be read more than one way. Therefore, my program added the label when the digits were wrong and the characters were wrong. Tio’s program read it to mean add the label if the characters are wrong.

I believe the fix would be to reword the sentence so only one reading is possible and add an example for exactly that. This is eye opening in terms of the work it takes to make sure the database and all rules are clear and can’t be read more than one way. Understanding this will encourage me to read the rules carefully before deciding on them.
